NAME
       etai - appointment scheduling for contractors and clients
       through messaging

OVERVIEW
       ETAi is a system where clients schedule, reschedule, and
       cancel appointments with contractors entirely through
       messages. There is no app for the client to learn. The
       client texts, the system books.

       The system has three services plus a UI:

       1. msg   - the messaging service      (messaging/, built)
       2. bus   - the central router         (bus/, to be built)
       3. cal   - the calendar side          (calendar-agent/ + the
                  Ambiguous workspace behind it)
       4. ui    - the video calling platform (frontend/, built)

PARTS

   msg
       The messaging service. Owns all inbound and outbound
       channels: iMessage via BlueBubbles today, SMS and voice
       later. Holds no scheduling logic.

       Inbound: the provider POSTs to /webhooks/bluebubbles,
       the message is normalized (channel, from, body,
       externalId, receivedAt, threadKey), deduplicated on
       externalId, and fanned out to every subscriber. The bus
       subscribes either by setting UPSTREAM_URL on msg (which
       auto-subscribes {UPSTREAM_URL}/webhooks/inbound) or by
       POSTing its URL to /subscriptions.

       Outbound: callers POST /send {to, body, threadKey}; msg
       picks the transport (bluebubbles when its env vars are
       set, else a stdout simulator). Contract in docs/PHONE.md,
       run details in docs/messaging.md.

   bus
       The central router and scheduling brain -- the "agent
       service" in docs/INTERFACES.md and docs/API.md.
       Everything crosses it; nothing talks point to point.
       The old agent/ service was merged into bus/ on
       2026-09-13; they were the same component.

       Inbound: POST /webhooks/inbound receives normalized
       messages from msg, classifies intent via Ambiguous
       assistant/chat (bus/ai.js), runs the scheduling loop
       (bus/loop.js) against the calendar adapter
       (bus/calendar.js -> bus/ambiguous.js), and replies via
       msg's /send. Per-thread state, dedup, jobs, and the
       action log live in bus/state.js; pre-job heads-up texts
       in bus/reminders.js. Also exposes POST /voice/turn
       (synchronous {reply}), /internal/digest, and
       /internal/client-update. Contract: docs/bus.md.

       Calendar notifications: POST /webhooks/calendar takes
       the feed from calendar-agent/notify.js and texts the
       contractor. Dedup on notification id.

   cal
       The calendar side has two layers.

       The contract: docs/CALENDAR.md defines five operations
       (availability, list a day, create, update, cancel) the
       bus can call over REST at CALENDAR_SERVICE_URL, or as an
       in-process CalendarProvider module. Everything
       Ambiguous-specific hides behind it.

       The brain: Ambiguous AI's workspace is the system of
       record (events, CRM, tasks, documents) and its Assistant
       classifies intent for the bus. calendar-agent/test.js
       shows the pattern: POST /api/assistant/chat with a
       natural language task, and the Assistant decides which
       calendar tools to call. The bus asks the Assistant for a
       JSON intent per message and runs the scheduling loop
       itself (bus/loop.js); the calendar CRUD goes through
       bus/ambiguous.js.

   ui
       The video calling platform in frontend/. Today it talks
       to the Ambiguous REST API directly from the browser:
       scheduling requests become real calendar events
       (resolve attendee, check free/busy, create event),
       anything else becomes a task, and the finished call
       transcript is stored as a workspace document. The
       planned path is ui -> bus -> cal so the bus sees every
       request, but that leg is not wired yet.

MODELS
       The wire contracts are JSON schemas in models/:
       phone-contract (inbound message shape), calendar-contract
       and calendar-event, assistant-chat-response,
       call-transcript, ambiguous-user, persona, task. Per
       AGENTS.md, schemas land before the code that uses them.

DATA FLOW
       Inbound, as wired today:

           client/contractor phone
             -> BlueBubbles webhook -> msg
             -> normalize -> dedup -> fanout
             -> POST {UPSTREAM_URL}/webhooks/inbound   (bus)
             -> intent classify -> Ambiguous assistant/chat
             -> scheduling loop -> Ambiguous calendar CRUD
             -> reply via msg /send

       Outbound:

           bus -> POST {MESSAGING_URL}/send -> msg
             -> transport -> client/contractor phone

       Calendar notifications:

           calendar-agent/notify.js
             -> POST {BUS_URL}/webhooks/calendar
             -> dedup -> contractor text via msg /send

       Video, as built today (bus bypassed):

           ui -> Ambiguous REST -> events/tasks/documents

       Video, as planned:

           ui -> prose -> bus -> cal AI

USERS
       Contractors travel to job sites and own the schedule.
       Clients text in to book, reschedule, or cancel.

       Contractors get a daily summary in the channel of their
       choice. Clients get notified when the contractor
       arrives, runs late, cancels, or reschedules.

GOTCHAS
       All messages go through the bus. The one exception that
       exists today is the ui, which holds an Ambiguous key in
       the browser and calls it directly -- fine for a demo,
       but the plan is ui -> bus -> cal so there is one place
       to audit and enrich.

       The bus is called the "agent service" in some older
       docs. Same component, two names -- and since 2026-09-13
       the agent/ directory literally lives inside bus/.

       The Assistant chat endpoint is contested ground:
       docs/calendar-agent.md and calendar-agent/test.js call
       POST /api/assistant/chat, while
       docs/ambiguous-integration.md reports that path missing
       from the live OpenAPI catalog and composes primitives
       instead. Verify against the workspace before building on
       either -- the spec, not the docs, is the truth.

       Exactly one brain subscribes to messaging's fanout.
       The bus is that brain. Anything else that also answers
       inbound texts produces double replies.

       Dedup is best-effort everywhere: msg dedups externalId
       in memory (a restart re-accepts once), so the bus should
       dedup too.

TRIED APPROACHES
       Separate agent/ and bus/ services: tried, then merged.
       Two processes both consuming inbound meant duplicate
       subscriptions and two sources of scheduling truth. The
       loop and the router are one component now.

       Direct msg -> cal connection: rejected. It saves a hop
       now but means notifications, video prose, and future
       weather enrichment each need their own wiring. One
       router, one place to change.

       MCP and the Ambiguous CLI for the ui: rejected -- MCP is
       a tool-calling transport, not something a browser should
       hold a key for, and the CLI shells out per call. Plain
       REST won. See docs/ambiguous-integration.md.
